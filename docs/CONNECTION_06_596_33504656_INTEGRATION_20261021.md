## Exact API wiring the #08 owner must review

The #596 worker currently exposes:
`CrossDeviceTransferJobs.start(input: TransferStart)`, `status()`,
`cancel()`, `TransferRemote.stat/hash/read/write/moveNoOverwrite`.
Its `TransferRemote.write(device, file, contentBase64, first, offset)`
does **not** supply a per-mutation `requestId`, authenticated connection
`epoch`, owner/project scope, or revocation callback. `TransferJob`
stores `bytesConfirmed` and the verified source hash but not the
revision-CAS `PendingTransferChunk` envelope used by #605.

#605's `DurableTransferContinuity` is an *optional, source-only*
connection-layer adapter; it is not injected into the #596 worker.
Required integration order:

1. Following #596 `start`'s authenticated owner and two-device grant,
   bind immutable `TransferBinding`:
   `jobId = TransferJob.id`, `ownerId = accountId`,
   `projectId`, `sourceDeviceId`,
   `destinationDeviceId = targetDeviceId`,
   `sourcePath`, `targetPath`, `stagePath`,
   `totalBytes = bytesTotal`, `sourceSha256 = sha256`.
   All values derive from the authenticated, persisted job, not the MCP
   request's unverifiable identity claims.
2. Source `AuthenticatedTransferRoute` from the trusted Broker session
   and CURRENT grants. Bind exact owner, project, both devices and the
   destination Agent WebSocket `epoch`. Neither an ACK payload nor a
   reused / stale Agent instance ID may set this epoch.
3. Provide a real durable `TransferCheckpointStore` with atomic insert
   and compare-and-swap(jobId, expectedRevision, next). Must use
   strict durable sequencing with the #596 job metadata and #08 receipt
   index; if two stores cannot commit atomically, preserve UNKNOWN and
   require explicit reconciliation. Do NOT claim that a second SQLite
   file automatically creates an independent anti-rollback root.
4. Supply live `TransferAuthorization(route,binding)` returning current
   account/project/source/destination grants and revocation state.
   A missing or failing authority MUST deny dispatch, late ACK,
   readback commit and finalization; source-only tests now exercise
   revocation before CAS, wrong project and stale epochs. Acquire an
   authority/dispatch fence preventing revoke between final check and
   network write. Checking only once at `transfer_start` is insufficient
   if revocation must stop in-progress work.
5. Before each <=65,536-byte destination mutation: compute exact chunk
   SHA-256 from bounded verified source bytes; persist `reserveWrite()`
   and its generated `PendingTransferChunk.requestId`, epoch, length,
   offset and hash. On CAS failure: NEVER dispatch. Extend #08-owned
   `TransferRemote.write` or its authenticated transport wrapper to
   propagate requestId and destination connection epoch and to reject
   responses from any other device, owner, epoch or request.
6. After `write` resolves, its ACK is correlation information only.
   For failed or lost ACK, persist UNKNOWN; do not re-issue the write.
   `DestinationReadback` must independently verify exact authorized
   destination stage bytes, offset, length and SHA. `reconcilePending`
   may then advance the monotonic offset to the next chunk. Partial
   stage, source mismatch, stale ACK, unexpected ID or revoked grants
   remain UNKNOWN; no blind replay.
7. On reconnect, the trusted Broker monotonically increases epoch,
   applying `onReconnect`. Fenced old-socket ACKs are never credited.
   The current pilot's different Agent v1.0.5 binaries are NOT a
   production validation of this protocol.
8. `cancel` while an unresolved mutation exists must preserve
   `cancel_pending`, prevent new writes and avoid deletion of an
   uncertain stage. `confirmPublished` only after #08 performs atomic
   no-overwrite publish AND `PublishedArtifactReadback` independently
   verifies destination device, size and full SHA. Caller-supplied hash
   strings are not completion evidence.
