# Dormant Admin Bridge command HTTP control plane (v1)

**Disabled by default.** Four new HTTP routes only operate when `createControlPlaneHttpHandler(service, { enableBridgeCommandTransport: true, ... })` is explicitly configured by a trusted runtime. The production Cloudflare Worker does NOT pass this option, and the web UI continues to display saved preferences with `applied:false`. This branch does NOT restart, stop, enable or disable a real Windows task.

## Routes

- `POST /api/v1/me/devices/bridge-command`: authenticated **device owner** must separately confirm with header `x-nexowire-confirm: bridge-command-issue-v1` and literal `confirmation: "APPLY BRIDGE MODE"`. This is distinct from `bridge-preference` and from merely saving AUTO/ON/OFF. Requires bound online FULL-access Windows device with broker-mode Agent and matching current saved preference. Queues a 120-second one-time record with a server-generated UUID. Never executes.
- `GET /api/v1/me/devices/bridge-command/status?requestId=...`: owner-only, account-bound status; never exposes the device credential, SHA-256 binding or the raw command input.
- `POST /api/v1/internal/device/bridge-command/claim`: caller must authenticate as the Hub service and present the **currently paired device credential** plus a specific request UUID. A durable D1 atomic claim prevents repeat claims; stale owner preference revisions, SAFE, offline, re-pairing and expired TTL reject the claim.
- `POST /api/v1/internal/device/bridge-command/receipt`: same Hub service + current paired-device credential; strict v1 receipt validator checks intended request/device/pairing/mode, bounded time, task state and the claimed authenticated health evidence. A successful store transition must occur only once and only if the current owner preference/device mode is still valid.

## Not production-ready

This is *server-side command lifecycle scaffolding*, not a complete secure Agent transport. No Hub relay operation, Agent opt-in, elevated local launcher, durable receiver-side replay log, authenticated device signing/provenance beyond Hub transport, user-presence check or actual Windows postcondition measurement is enabled here. Receipt `brokerHealth` is still only a reported field unless generated by the trusted Agent-side measurement flow. The public Worker does not opt in; **never enable** until the full device command path is reviewed with an adversarial threat model and the privileged runtime rollout blocker [#271](https://github.com/Naveax/Nexowire/issues/271) is cleared. On rollout do NOT convert existing saved preferences into commands or infer that a queued/claimed status means an action happened.

The focused tests use temporary in-memory stores and fake authenticated identities, without contacting or modifying a real device.
