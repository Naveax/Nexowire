## Separate three different claims

**(1) OS-supported assistance route.** On Windows 10/11, Microsoft documents a conditional UIAccess/Remote Assistance standard-user *credential prompt* path: an intentionally approved session and qualified, signed, protected UIAccess application, subject to the effective local policy. This is interactive human help, **not** an instruction to change policy or inject remote clicks. **Administrator UAC consent prompts are not changed by the UIAccess policy.** The policy is disabled by default.

**(2) Actual OS result.** The Nexowire read-only `windows_uac_status` call only observes a `consent.exe` process in the caller's session; a visible process, `FORBIDDEN` secure desktop, screenshot, helper `ACK`, HTTP 401, "FULL", "CORE" or Broker telemetry is never evidence that credentials were supplied or an elevated image started. Windows does not provide a general-purpose cryptographically signed UAC approval certificate for Nexowire to blindly trust. To claim *a resulting elevated launch* an independent native Windows authority would have to attest the **current actual process image**, publisher/image/import provenance, effective high token, request/nonce, owner/device/session and trustworthy result. This capability remains **NOT DEPLOYED / BLOCKED** and isn't generated by these tests.

**(3) Once-enrolled Broker operation.** A legitimate administrator may once install and authorize a signed, immutable, protected high-token Broker. Future authorized CORE commands can then use the existing Broker **without UAC on every command**, but only while the exact owner/device/session/current epoch/capability and command constraints still pass. Revoke, wrong signed image, stale epoch, changed publisher, missing high token, no successful independent postcondition or lost ACK mean DENY/UNKNOWN, **never automatic RunAs, a fresh UAC prompt, desktop switch or blind replay**.
