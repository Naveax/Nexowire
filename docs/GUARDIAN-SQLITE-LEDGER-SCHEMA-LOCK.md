# Guardian SQLite replay-ledger schema lock (source-only)

The Guardian's preprovisioned SQLite replay database uses a permanent per-request key. The initial factory checked only its application ID and whether the replay table ended with `STRICT`. This was insufficient: a different `STRICT` table without a unique request digest, or an unreviewed `AFTER INSERT` trigger that deletes the row, can make the same authenticated Hub command appear valid repeatedly.

The read-only initial trust check now compares the complete normalized SQLite `CREATE TABLE` statement against the fixed reviewed `GUARDIAN_REPLAY_SCHEMA`, including the request_digest PRIMARY KEY and each exact digest constraint. It permits exactly one user-defined SQLite schema object, that table, and refuses persistent extra tables/views/triggers and connection-local TEMP objects/triggers.

This is a **fail-closed check at ledger opening**, not a migration or schema repair. Existing correctly provisioned test databases continue to work. Test cases explicitly reject a syntactically valid STRICT table missing its unique primary key, an AFTER INSERT DELETE trigger, an extra data table and a connection-local temporary trigger. Normal transactional one-use reservations, signed commands, cross-process concurrency and revocation tests remain passing.

**Limitations:** Exact DDL checking does not establish that the filesystem and SQLite runtime are trusted, prevent same-process malicious code from mutating schema after initialization, guarantee controller flush after a power failure or solve atomic cloud owner revocation. The module is still deliberately inert; no production database is provisioned and no Guardian task, Agent, ACL, Cloudflare Worker or D1 data is modified. Security issue #271 is not fixed and privileged Windows ON/OFF remains blocked.
