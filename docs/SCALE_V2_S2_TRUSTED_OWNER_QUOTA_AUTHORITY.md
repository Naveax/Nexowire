## The problem and the architecture

1. **Transport budget**: Count every local ingress arrival (metadata, auth failures, retries, rejected methods and tool calls) once against an **operator-signed tunnel+calling-application identity**. The existing trusted `ProposedAllIngressTransportMeter` is the **only local 600/rolling-minute limiter**, and its operator-bound scope comes from `createSignedStagingTransportBudget`. Never derive transport identity from request HTTP headers, JSON or device-controlled settings.
2. **Logical tool entitlement**: After a transport request is admitted, an independently authenticated first-party principal's current account, session generation, device ownership, mode and plan are all checked by the **owner-controlled shared database transaction**. Only a newly admitted, eligible logical tool invocation reserves 1 unit from the account's UTC daily allowance. Auth failures and metadata do **not** spend daily logical tool allowance.
3. **Trusted host rather than customer PC**: Database state belongs to the operator, not the user's computer. A user who controls their local SQLite database can forge limits. Two independent SQLite connections to one shared owner-side file can use identical counters; this does not automatically give geographically distributed network access or replicated consistency. The user PC still executes its tools using its existing Native Agent, after an additional independent operation authorization check.

## Security and quota contracts

- `bindSignedIngress()` supplies the signed public HTTPS `/mcp` route to the existing all-arrivals meter, checks the pinned Ed25519 operator verification key and live route generation for **each** invocation. The signing PRIVATE key exists only at the trusted owner, never on a customer-controlled computer. The genuine OpenAI Secure MCP Tunnel metadata issuer is still **unverified**, so tests use ephemeral fake operator keys.
- `reserveLogicalTool()` accepts a caller bearer that is verified by a **server-only injected first-party authenticator**. The test authenticator is a stub. The request **cannot specify a plan, daily allowance, account ID or verified boolean**. It supplies a device ID, unique logical invocation ID and **trusted server-canonical** operation fingerprint and read/write classification. Only the real MCP dispatcher can determine tool category and fingerprint; customer-controlled classifications would be insecure.
- A **single `BEGIN IMMEDIATE` transaction** checks account active state, auth session generation, current owner device and enabled state (actual Agent online presence still requires a separate trusted live check), Safe vs Full access mode, current server-side plan, global replay ID, daily counter, then reserves the invocation and increments the daily counter. Expired/revoked token generation, transferred/disabled device, or a write on Safe mode does not reserve quota. A duplicate request reuses **no quota and must not execute again**; a changed device/fingerprint with the same logical invocation ID is rejected as collision. These checks do not cancel actions that already started.
- Future prototype logical limits: Free 1,000/day; Plus 5,000/day; Pro 10,000/day; server-verified Custom integer 100..850,000/day. **These are OFF** and not synchronized with payment orders. Raising the limit only changes the numerical ceiling; device permissions and tool authorization remain independent. Downgrades block new operations after the new limit is reached; previously accepted invocations are not erased.
- This staging authority **does not call** the original `ProposedOwnerHostedCustomUsageMeter` which also has a 600/minute admitted-tool ledger; using both would double-throttle. Here the transport gate is counted **once** at the ingress, while the per-account daily tool ledger is counted **once** at owner-side reservation.
- A returned `status: 'reserved'` is a quota decision **NOT** a tool execution authorization, legal permission or payment receipt. The explicit `authorizesToolExecution:false` field prevents callers from treating this as proof of OS/broker permission. Real device command permission, consent, in-flight revocation and actual tool result remain separate safety layers.
- The replay ledger intentionally has no pruning, so long-running accounts create durable storage cost, lock contention and compaction requirements. A reservation counts even if tool execution subsequently fails: retries must use the same idempotency key, not produce uncontrolled new charges. Final refund/failed-call billing semantics require an explicitly reviewed state machine.
- The SQLite proof uses a **single owner-controlled database**, not one local PC database per subscriber. Stronger distributed guarantees will require authenticated cross-host RPC, high-availability/replication, secure authority keys, provider identity, lock contention/soak measurements, failover, cost and honest disclosure. An operator-hosted SQLite server is not itself a network-distributed product.

## Production acceptance blockers

1. Enroll and authenticate real `account_id`, OAuth epoch, device ownership and signed verified user/tunnel/app identities to the trust source. Current production OAuth is not wired to these staging prototypes.
2. Add a **secure owner-operated network transport** for clients from any city/country, with authentication, certificate validation, request signing or mTLS, bounded timeouts, replay resistance and strict command routing. Use the already owned PC/server if the user requires no incremental operator cloud bill. **Do not open raw DB or Hub /agent to public Internet.** Fail closed when trusted server unavailable.
3. Owner key custody, signed plan/cancellation and entitlements from approved billing provider, verified signup/checkout legal and privacy notices, auditable quota decisions, idempotency retention/refund policy and account recovery. Actual Free remains 1,000 **weighted credits/month** and this module is not imported by production billing/Hub/Worker code.
4. Real end-to-end `ChatGPT -> public HTTPS MCP -> verified owner ingress -> user local PC Agent` permissions/revocation, cross-network NAT/CGNAT, distributed quota and all-ingress throttling under users sharing the same tunnel. Note OpenAI may count requests before they reach our origin; local 429 does not refund the provider budget.
5. Full-scale shared authority and PC load test, 600/min for actual real transport, 850,000/day sustained 24h load with measured CPU/RAM/IO/bandwidth/p95/p99, disk usage, failures, provider rate throttles and actual **zero incremental operator cloud invoice**.
