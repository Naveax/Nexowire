# Guardian local SQLite replay ledger: stronger durable foundation (inert)

PR #354 introduced a crash-safe-on-normal-restart, exclusive-create per-request tombstone. Its important limitation: an operating system / storage power loss may forget a newly created directory entry even when the tombstone's content was flushed. Before ANY Windows privileged task actuation, the Guardian needs a reviewed persistent local journal.

This separate, **unused and source-only** module evaluates the built-in Node `node:sqlite` `DatabaseSync` with SQLite **rollback journal DELETE + synchronous EXTRA**, `BEGIN IMMEDIATE`, a strictly unique SHA-256 request digest primary key and committed transaction BEFORE a future OS operation. It uses `INSERT OR IGNORE` for one winner, handles concurrent database connections, and stores only hashed device, pairing and owner-preference revision values. The provisioned database must have the pinned application ID and STRICT schema; it refuses unprovisioned databases and never installs or migrates a real production database automatically.

Tests verify an exclusive winner among 20 asynchronous reservations, **exactly one winner among four independently running OS processes** sharing the same database, reopening after normal close, a separate Node child process exiting **without closing its database handle** after a committed reservation, wrong application ID, malformed requests, ACL refusal, revoked pairing before commit, exact owner-approved request ID and revision mismatches, and revocation after commit (consumes but does not authorize). Additional synthetic integration tests couple the existing pinned-Hub Ed25519 command verifier to this SQLite reservation: valid signed commands are one-use across database reopen, altered signatures fail *before* writing a replay row, and locally observed owner revocation prevents a reservation. The test database and private ACL callback are isolated disposable fixtures, **not** trusted Guardian identity or live proof.

The only production-oriented factory pins `C:\ProgramData\Nexowire\bridge-guardian\state\replay.sqlite` and checks the Guardian launcher and each ancestor directory/database owner/write ACL before opening it. A separately owner-approved protected installer must pre-provision and attest the database, owner credentials and Guardian executable. This source PR does not create a production database.

**Critical remaining limits:**
- `synchronous=EXTRA` requests stronger SQLite/OS flush behavior but does not prove that a specific storage controller respects flush or eliminate all filesystem/hardware crash failure modes. Real forced-power-loss device tests and complete journal/sidecar ACL analysis remain necessary.
- A SQLite transaction cannot atomically commit with Cloudflare D1 owner revocation. The local reserve callback now requires independently trusted **exact owner-approved request UUID and matching preference revision** in addition to current pairing/authorization, but a protected authenticated session/lease protocol tied to Cloudflare approval is still necessary, and remote revocation may race even the post-commit re-read.
- Database deletion/replacement, hardlink aliases, NTFS reparse races, OS integrity and storage rollback require separately protected Guardian measurements and secure install/rollback design.
- A valid local replay reservation is **NOT Windows operation authorization**. There is no Windows Scheduled Task start/stop, process lifecycle control, cloud command transport, key enrollment, production D1 migration or Worker deployment.
- Security blocker [#271](https://github.com/Naveax/Nexowire/issues/271) is still OPEN and must be independently remediated before any real ON/OFF feature.

This implementation supplements rather than silently replaces PR #354. It is inert until explicitly integrated after protected Guardian installation and security acceptance.
