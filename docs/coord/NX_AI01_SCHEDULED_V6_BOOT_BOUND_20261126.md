# AI-01 / AI-05 scheduled v6 boot-bound interface proposal (2026-11-26)

Base #1369 155f876dd63732d9fa6126a30c62d09d8398e1b7. The existing persistent AI05 v1 update fence survives reboot; its in-memory fence ownership and forward hashes do not. Do not reconstruct forward permission from task Enabled, fence bytes, wall clock, or a previous success status. No AI05 source changes or new launch sink.

The staged SYSTEM launcher is now an inert BOM-bearing v6 artifact, not a supervisor. It cannot read credentials, invoke a legacy helper, or start an Agent even with an old helper installed. Historical owner launcher rendering and existing NWJOB3 readback remain untouched. Existing installed/staged legacy launchers are not retroactively changed.

Proposed contract for AI05 review: protected provider supplies a kernel-derived boot epoch and fresh attempt ID, current device/installation, monotonic fence generation and exact fence digest, task definition/SID/session, source and runtime manifest, exact launcher/helper hashes and file incarnations. Forward issuer signs this scope, independent native release issuer signs the same scope plus the forward envelope digest and exact suspended guardian/root PID+FILETIME+session. Distinct pinned Ed25519 keys and domain separators. Candidate leases max 300s forward/30s release, release within forward lifetime. Boot mismatch, changed attempt or any observed binding rejects previous receipts, even with valid signature. No agreement with AI05 claimed yet; these lease bounds are proposed defaults.

Read-only bridge checks installed file identity against the signed binding. Stage-only marker is not accepted as a protected supervisor. The signature review does not authenticate the observation provider and returns no grant. Before any positive activation a protected service must supply independent pinned trust, read current boot epoch under held handles, atomically consume each attempt in a durable non-rollback ledger, bind scheduler action and loaded image/IPC, and retain proof until STOP/recovery. An old boot may not reuse prior forward permission; normal restart requires fresh independent same-boot authorization. AI02 recovery authority is separate. No automatic recovery or legacy cutover.

VM acceptance: verify kernel boot epoch across actual reboot, prior signed grants invalid, no root effect on stale/absent/malformed proof, exact loader/guardian identities, fresh independently consumed grant, Session0 SYSTEM with prelogin transport, STOP/timeout Job empty and exact root signaled, high/linked token physical negatives, interrupted migration with preserved fence/receipts. No production activation while provider/VM proof absent. No tests or pins removed; AI00/AI08 own exact source/count reconciliation.
