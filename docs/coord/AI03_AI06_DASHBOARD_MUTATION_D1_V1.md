# AI-03 / AI-06 durable dashboard mutation contract v1

Backend source only; coordinate migration, browser and API deployment as one candidate. No native authority, capability, approval, OS effect, local STOP or drain is granted.

- POST /api/v1/pairing: X-Nexowire-Mutation-Id: pairing-v1:<lowercase 64 hex>. Required deviceId and deviceName. Server binds authenticated owner, device, route and normalized name to the SHA256 payload. #1345 already sends this stable native-session correlation identity. It is not proof of native state; a malicious client inventing another identity is not the same-intent dedup guarantee. No token in durable mutation ledger or status; original first caller alone can receive the challenge token.
- GET /api/v1/me/dashboard: device.coreMutationRevision is a positive server-side integer or null (unavailable). This is not the remote authorization epoch, CORE grant generation, local consent or lease.
- POST existing core-preference / core-enrollment-request: X-Nexowire-Mutation-Id: core-v1:<lowercase UUIDv4> plus JSON expectedRevision from the exact owner/device fresh GET. Preserve all existing typed confirmation headers. No missing-ID or missing-revision compatibility mutation route. Enable/consent require configured independent consent verifier, current remote authorization and existing readiness; OFF does not require issuer. Different UUIDs with stale revision or identical already-requested semantic state cannot repeat the write. Fresh explicit OFF uses a new UUID and fresh revision. No automated retry.
- GET /api/v1/me/mutations/status?mutationId=<exact opaque ID>: authenticated owner only. 200 {mutationId,deviceId,kind,state,expectedRevision}. APPLIED means only committed preference/enrollment request or challenge creation, never device delivery, pairing consumption, physical CORE or STOP. DENIED is terminal CAS/semantic conflict. PENDING is unresolved and cannot be replayed. 404 is absence of visible record, not a retry instruction. Never infer terminality from generic dashboard preference.
- Exact duplicate POST returns 409 DASHBOARD_MUTATION_ALREADY_APPLIED / DASHBOARD_MUTATION_REVISION_OR_STATE_CONFLICT; a pending same ID returns 503 DASHBOARD_MUTATION_OUTCOME_UNKNOWN. Conflicting payload/scope or foreign owner returns generic 409. No plaintext pairing token returned on duplicates. Lost ACK remains uncertain until exact read-only status. Never mint a replacement mutation ID automatically.
- SQL migration 0090 creates durable owner/device/payload-bound claims and revision tombstones. D1 batch claim, guarded write, terminal readback are atomic; execution nonce binds only winning invocation. Revision advances when actual readiness, owner/credential, maintenance, bridge, enrollment, CORE generation/revoke or remote epoch changes. Historical tombstones survive device deletion. No expiration/replay path.
- Tests use on-disk SQLite, actual migrations and separate connections, with post-COMMIT ACK loss. They are not hosted D1 acceptance or physical consent. Existing MemoryControlPlaneStore cannot admit browser mutations. Legacy in-process service methods remain for current trusted internal use; public HTTP routes never use their unguarded mutation paths.
